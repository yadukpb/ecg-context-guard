# 07 — Deploying for free (Vercel + Render + MongoDB Atlas)

All three free, none need a credit card. The one real tradeoff: Render's free web
services sleep after ~15 minutes idle and take 30-60s to wake on the next request — fine
for a demo you walk someone through live, mildly annoying for a cold unannounced link.

This is a manual, one-time setup. The repo already has everything needed
(`render.yaml`, env-var-driven config) — what's left is account creation and copying a
handful of URLs/secrets between three dashboards, none of which can be scripted from here
since each needs your own login.

## 1. MongoDB Atlas (database)

1. Sign up at mongodb.com/cloud/atlas — no card required for the free tier.
2. Create a free **M0** cluster (any region).
3. **Database Access** → add a database user (username + password — save these).
4. **Network Access** → add IP address `0.0.0.0/0` ("allow from anywhere"). Render's free
   tier doesn't have a static IP to allowlist more narrowly.
5. **Connect** → "Drivers" → copy the connection string. It looks like
   `mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority`.
   Add a database name before the `?`: `.../ecg_context_guard?retryWrites=true...`.
   This full string is your `MONGO_URI`.

## 2. Render (both backends)

1. Sign up at render.com with GitHub — no card required for free web services.
2. **New** → **Blueprint** → connect the `ecg-context-guard` repo. Render reads
   `render.yaml` at the repo root and proposes two services:
   `ecg-context-guard-api` (Node) and `ecg-context-guard-detector` (Python).
3. Apply the blueprint. Both services deploy, but will fail to start correctly until the
   `sync: false` env vars below are filled in (Render's blueprint UI prompts for these,
   or set them after under each service's **Environment** tab):

   **ecg-context-guard-api:**
   - `MONGO_URI` — the Atlas connection string from step 1.
   - `TRANSPORT_SECRET` — any long random string you make up (e.g. `openssl rand -hex 32`).
   - `DETECTOR_BASE_URL` — leave as a placeholder for now; comes back in step 4.
   - `CLIENT_ORIGIN` — leave as a placeholder; comes back in step 4.
   - (`JWT_SECRET` is auto-generated by the blueprint — leave it.)

   **ecg-context-guard-detector:**
   - `TRANSPORT_SECRET` — **the exact same string** you used for the API service above.
   - `EXPRESS_BASE_URL` — leave as a placeholder for now.

4. Once both services finish deploying, each has a URL like
   `https://ecg-context-guard-api.onrender.com`. Go back and fill in:
   - API's `DETECTOR_BASE_URL` = the detector service's URL.
   - Detector's `EXPRESS_BASE_URL` = the API service's URL.
   Saving an env var triggers a redeploy of that service — expected.

## 3. Vercel (frontend)

1. Sign up at vercel.com with GitHub — no card required.
2. **Add New** → **Project** → import the `ecg-context-guard` repo.
3. In the import settings: **Root Directory** → `apps/web` (this is a monorepo; Vercel
   needs to know which subfolder to build). Framework preset should auto-detect as Vite.
4. **Environment Variables** → add `VITE_API_BASE_URL` = the API service's Render URL
   from step 2.4 (e.g. `https://ecg-context-guard-api.onrender.com`).
5. Deploy. Vercel gives you a `https://<project>.vercel.app` URL.
6. Go back to Render → API service → set `CLIENT_ORIGIN` = that Vercel URL (exact
   origin, no trailing slash) → save (redeploys).

## 4. Seed the production database

The demo login (`demo@ecg-guard.local` / `demo1234`) and demo patients only exist if
seeded. From this machine, run the seed script once against the *production* Mongo:

```bash
cd apps/api
MONGO_URI="<your Atlas connection string>" node src/seed.js
```

This connects directly to Atlas from your laptop and writes the demo user + patients —
no need to run it on Render itself.

## 5. Verify

- Open the Vercel URL. First load after any backend idle period takes 30-60s (cold
  start) — this is expected on the free tier, not a bug.
- Log in with the demo credentials, open a patient, start a stream. If nothing happens,
  check both Render services' **Logs** tabs first — almost always a mismatched
  `TRANSPORT_SECRET` (must be byte-identical on both services) or a `CLIENT_ORIGIN`/CORS
  mismatch (must be the exact Vercel origin, protocol and all).

## Known free-tier caveats, stated plainly

- **Cold starts.** Both Render services spin down after ~15 min idle. A panel demo
  should be "warmed up" (visit the site, let it finish loading) a minute or two before
  presenting live.
- **In-memory MIT-BIH/BIDMC cache resets on every cold start.** The detector re-fetches
  whichever records are first requested after waking — a few extra seconds on the very
  first stream start after idle, not a bug.
- **MongoDB Atlas M0 is a shared, small free cluster** — fine for a demo's data volume,
  not meant for production traffic.
